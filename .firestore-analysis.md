# DailyHabits Firestore analysis

Generated from the vanilla JavaScript application before creating `firestore.rules`.

## Access model

- Authentication: Firebase email/password.
- Every cloud path is nested under `users/{uid}`.
- The client only reads collections already scoped to the authenticated UID; it uses no `where`, `orderBy`, or `limit` clauses.
- Demo mode never reads or writes Firestore.

## Paths and operations

- `users/{uid}/profile/account`: owner read, create, update. Fields: `name`, `email`, `weekStart`, `updatedAt`.
- `users/{uid}/habits/{habitId}`: owner list/get/create/update/delete. Fields: `name`, `icon`, `category`, `color`, `frequency`, `startDate`, `goal`, `archived`, `createdAt`, `updatedAt`.
- `users/{uid}/habits/{habitId}/completions/{yyyy-mm-dd}`: owner list/get/create/delete; update is validated even though the current client toggles by create/delete. Fields: `completed`, `completedAt`.
- `users/{uid}/notes/{noteId}`: owner list/get/create/update/delete. Fields: `text`, `date`, `createdAt`, `updatedAt`.

## Devil's advocate review

- Public reads: denied because every allow condition requires `request.auth` and matching path UID.
- Cross-user access: denied because `request.auth.uid` must equal `{uid}`.
- Ownership hijacking: no owner/UID field is writable; ownership comes only from the immutable path.
- Schema pollution: all create/update validators use `keys().hasOnly(...)`.
- Oversized input: every string has an explicit maximum length.
- Type juggling and required-field omission: every validator checks required keys and types.
- Invalid enums: category, frequency, and week-start fields use fixed allowlists.
- Timestamp manipulation: client timestamps must equal `request.time`; `createdAt` is immutable.
- Orphaned writes: habit and note operations require the owner's profile; completion operations also require the parent habit.
- Query mismatch: all queries are directly scoped under the authenticated user's path, matching the ownership rules.
- Privilege escalation: the schema contains no role, permission, admin, owner, or sharing fields.
- Counter/action replay: not applicable; the data model contains no shared counters.
- Path traversal: clients do not store document or storage paths as fields.

This is a static rules review. Emulator-based multi-user tests are still recommended before a broad production launch.
